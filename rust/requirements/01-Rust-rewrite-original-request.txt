## 5. Detection Engine — Reliability and Low Latency

Inspect the attached original AutoHotkey script to understand the intended behaviour.

The original script uses:

- A 12-pixel detection radius.
- Approximately 5 ms between scans.
- Green-dominance detection.
- Hold-key activation.
- A 120 ms rearm delay.
- Mouse-click output.

The previous implementations suffered from inconsistent detection and repeated input events.

Do not reproduce those defects.

### Detection requirements

Implement an efficient native colour-detection pipeline.

Use GPU acceleration where appropriate.

Support configurable HEX colour tolerance.

The system must correctly distinguish the selected colour from unrelated colours.

Use a strict event-driven state machine:

`IDLE → ARMED → FIRED → WAITING_FOR_CLEAR → ARMED`

Behaviour:

- Holding the configured key enables monitoring.
- Detecting the target colour sends one configured output.
- Continuous colour presence must not cause duplicate outputs.
- A confirmed disappearance followed by reappearance allows another output.
- Releasing Hold immediately disarms monitoring.
- Disabling the application clears pending events.
- Changing bindings or detection mode resets the state safely.

### Duplicate-trigger prevention

Do not rely solely on a large fixed cooldown.

Use detection-state transitions to prevent repeated output.

The same continuous highlight must produce only one trigger event.

A genuinely new highlight may produce another event after the previous detection has cleared.

Use a small configurable clear-state debounce to avoid false rearming caused by brief capture glitches.

Prevent multiple processing threads from dispatching the same event.

### Performance

Optimise for low latency.

Use:
- Efficient Direct3D 11 capture where appropriate.
- Reusable GPU resources.
- Small detection regions.
- Minimal CPU/GPU synchronisation.
- High-resolution monotonic timing.
- Efficient input dispatch.

Avoid:
- Full-screen CPU pixel scanning.
- Per-frame allocations.
- UI processing in the detection loop.
- Unnecessary blocking operations.
- Duplicate capture loops.

Do not claim guaranteed sub-1ms end-to-end latency or perfect parries.

Prioritise reliable detection and accurate event handling over unrealistic performance claims.
